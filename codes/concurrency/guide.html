B

先看一个场景

你在写一个 RAG 脚本，要调 9 次模型接口。每次等 0.2 秒。

串行跑完要 1.8 秒。你听说「加并发就快了」，于是开了 9 个线程，确实降到 0.2 秒。

第二天你把同样的写法用在一个本地文本处理函数上。那个函数要算 0.2 秒的纯 Python。你开 9 个线程，结果还是 1.8 秒。

这不是代码写错了，是瓶颈不同。并发只解决一类问题：你在等。它解决不了另一类问题：你在算。

C

并发不等于并行

两个词中文都像「一起跑」，英文也不是同义词。

词 意思 类比
并发 concurrency 同时处理多件事 一个厨师轮流看三口锅
并行 parallelism 同一时刻真在做多件事 三个厨师各看一口锅

并发是结构，并行是物理。一个核也能并发，靠的是「谁在等就切走」。多核才能并行。

  • 卡在等网络回包，CPU 闲着 → 切走干别的，一个核够用。
  • 卡在算，CPU 满着 → 必须多弄几个核。
D

三种工具，先认脸

单位 谁调度 内存 启动 / 切换成本 能并行吗
进程 操作系统 独立 新建约几十毫秒 能，各用各的核
线程 操作系统 共享 切换微秒级 Python 里受限
协程 你自己写的循环 共享 切换纳秒级 不，单线程

三句话：进程最重也最独立；线程最常用也最容易写出 bug；协程最轻但要求全链路配合。

E

GIL：一次只放一个人进屋

CPython 的 GIL 保证同一时刻只有一个线程在跑 Python 字节码。

4 次纯 Python 计算，每次约 0.12 秒
串行            0.46s
4 个线程        0.46s   ← 一点没快
4 个进程        0.19s
4 个子解释器    0.16s

线程数翻了 4 倍，时间一模一样——四个线程在轮流用同一个工位。

那线程还有什么用？有。等的时候，GIL 是放开的。

F

线程能加速「等」，不能加速「算」

同一套线程池，换成只等待的任务，结论立刻反转。

8 次网络等待，每次 0.2 秒
串行        1.63s
8 个线程    0.21s   ← 快 8 倍
8 个协程    0.20s

线程发出请求后在等回包，碰不到 Python 代码，于是放开 GIL。别的线程立刻进来。

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(8) as pool:
    results = list(pool.map(fetch, urls))

I/O 密集就该这么写。别自己 Thread 加锁拼一个池子。

G

竞态：最贵的 bug

线程共享内存。共享就会撞车。

def bump(counter):
    current = counter[0]
    time.sleep(0)          # 真实代码里是打日志、记 metrics
    counter[0] = current + 1

4 个线程各执行 2000 次，期望 8000。实测：

期望 8000   实得 2020   丢了 5980

两个线程都读到 10，都算出 11，都写回 11——一次自增凭空消失。

紧凑的 counter[0] += 1 有时「测出来没事」，那是运气：解释器碰巧没在读和写之间切换。一加日志就炸。

import threading

lock = threading.Lock()

def bump(counter):
    with lock:
        counter[0] += 1

加锁后：8000 / 8000。用 with lock:，锁里别放慢操作；能不共享就别共享。

H

进程：绕开 GIL 的过路费

from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(4) as pool:
    results = list(pool.map(cpu_work, [n] * 4))
代价 说明
启动 每次建池约几十毫秒
传数据 参数和返回值都要 pickle
传不了 lambda、闭包、连接、生成器

硬约束：交给进程池的函数必须在模块级；脚本入口写 if __name__ == "__main__":。

I

asyncio：一个线程怎么同时等很多事

协程在一个线程里靠「主动让位」并发。await 是让位点。

一个阻塞调用毁掉全部：

time.sleep      1.02s    ← 5×0.2，没有并发
asyncio.sleep   0.20s    ← 全并发

非异步库丢进线程：await asyncio.to_thread(blocking_func, arg)。

需求 写法
一起等，按输入顺序收 await asyncio.gather(*coros)
谁先回来先处理 async for / as_completed
单个超时 await asyncio.wait_for(coro, timeout=0.2)
J

生产三件套：限流、失败、超时

sem = asyncio.Semaphore(3)

async def one(i):
    async with sem:
        return await call(i)

await asyncio.gather(*[one(i) for i in range(9)])

9 个 0.2 秒请求、上限 3 → 实测 0.60 秒，峰值 3。

results = await asyncio.gather(*coros, return_exceptions=True)
await asyncio.wait_for(coro, timeout=0.2)  # 超时会取消目标
K

选型：拿到活先问三句

  1. 只有一个？串行。
  2. 在算？进程。线程白搭。
  3. 在等，路数很多？协程加限流；几十路以内线程池更省心。

先串行跑通，再改并发。 并发引入的 bug 会掩盖逻辑错误。

M

两分钟复盘

  1. 选型三问：一个？→串行。算？→进程。等？→线程或协程+限流。
  2. GIL：算的时候线程轮流；等的时候 GIL 放开。
  3. 竞态：共享读-改-写必须加锁，或别共享。
  4. 限流 / 失败 / 超时：Semaphore、return_exceptions=True、wait_for。
  5. 阻塞毁掉协程：time.sleep / 同步 HTTP 会卡住整条循环。
  6. 顺序：as_completed 按完成；gather 按输入。
  7. 笔记本：别 asyncio.run；进程池函数放模块里。

最后一句话

并发不提升单次速度，只提升吞吐。只有当「等」明显拖慢整体，才值得付出调度、竞态、超时的复杂度。否则串行就是最好的并发。
