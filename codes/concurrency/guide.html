A

先看一个场景

你在写一个 RAG 脚本，要调 9 次模型接口。每次等 0.2 秒。

串行跑完要 1.8 秒。你听说「加并发就快了」，于是开了 9 个线程，确实降到 0.2 秒。

第二天你把同样的写法用在一个本地文本处理函数上。那个函数要算 0.2 秒的纯 Python。你开 9 个线程，结果还是 1.8 秒。

这不是代码写错了，是瓶颈不同。并发只解决一类问题：你在等。它解决不了另一类问题：你在算。

后面的每一节都在回答同一件事——手上的活，到底是等，还是算。

B

并发不等于并行

两个词中文都像「一起跑」，英文也不是同义词。

词 意思 类比
并发 concurrency 同时处理多件事 一个厨师轮流看三口锅
并行 parallelism 同一时刻真在做多件事 三个厨师各看一口锅

并发是结构，并行是物理。一个核也能并发，靠的是「谁在等就切走」。多核才能并行。

所以判断标准只有一条：这件事卡在哪。

  • 卡在等网络回包，CPU 闲着，那就切走干别的，一个核够用。
  • 卡在算，CPU 满着，那就必须多弄几个核。

这个区分会一直用到最后，别跳过。

C

三种工具，先认脸

Python 里能「同时处理多件事」的单位只有三个。

单位 谁调度 内存 启动 / 切换成本 能并行吗
进程 操作系统 独立 新建约几十毫秒 能，各用各的核
线程 操作系统 共享 切换微秒级 Python 里受限
协程 你自己写的循环 共享 切换纳秒级 不，单线程

三句话记住：

  • 进程最重，也最独立。它绕开一切 Python 层面的限制。
  • 线程最常用，也最容易写出 bug。共享内存是双刃剑。
  • 协程最轻，但要求全链路配合。一处阻塞就全废。

下一节解释「Python 里受限」这四个字，它是很多困惑的源头。

D

GIL：一次只放一个人进屋

CPython 里有一把全局锁，叫 GIL。它保证同一时刻只有一个线程在跑 Python 字节码。

想象一间只有一个工位的房间。四个人（线程）都想进去干活。谁进去，谁干一会儿，时间到了出来换人。

这带来一个反直觉的结果：

4 次纯 Python 计算，每次约 0.12 秒
串行            0.46s
4 个线程        0.46s   ← 一点没快
4 个进程        0.19s
4 个子解释器    0.16s

线程数翻了 4 倍，时间一模一样。因为那 4 个线程在轮流用同一个工位。

那线程还有什么用？有。等的时候，GIL 是放开的。

E

线程能加速「等」，不能加速「算」

同一套线程池，换成只等待的任务，结论立刻反转。

8 次网络等待，每次 0.2 秒
串行        1.63s
8 个线程    0.21s   ← 快 8 倍
8 个协程    0.20s

道理不难：线程发出请求后就在等回包，这段时间它碰不到 Python 代码，于是主动放开 GIL。别的线程立刻进来干活。

所以「线程有用吗」这个问题没有统一答案。先看你在等还是在算。

一个能直接抄的骨架

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(8) as pool:
    results = list(pool.map(fetch, urls))
  • pool.map 按输入顺序返回结果。
  • 出异常时，map 会在取结果那一刻抛出。
  • 想拿回完成的顺序，换 as_completed。

I/O 密集就该这么写。别自己 Thread 加锁拼一个池子。

F

竞态：最贵的 bug

线程共享内存。共享就会撞车。

看这段代码，读和写之间夹了一次调用：

def bump(counter):
    current = counter[0]
    time.sleep(0)          # 真实代码里是打日志、记 metrics、发请求
    counter[0] = current + 1

4 个线程各执行 2000 次，期望 8000。实测结果：

期望 8000   实得 2020   丢了 5980

为什么？两个线程都读到 10，都算出 11，都写回 11。有一次自增凭空消失。

这就是竞态：结果取决于两个线程谁先谁后，而你控制不了。

更阴的地方

同一台机器上，把 sleep(0) 去掉，改成紧凑的 counter[0] += 1 循环：

紧凑 += 循环    8000 / 8000   一次都没丢

看起来安全，其实是运气。这台机器的解释器只在特定位置切换线程，紧凑循环恰好躲开了。

# 这就是为什么不能靠「我测过没问题」
counter[0] += 1        # 三个动作：读、加、写

一旦你把「读」和「写」拆开，中间插进任何一次调用，它就炸。而你加日志那天，正好就是拆开的那天。

唯一的解法

import threading

lock = threading.Lock()

def bump(counter):
    with lock:
        counter[0] += 1

加锁后：期望 8000，实得 8000。

  • 用 with lock:，不要手写 acquire / release。异常路径才不会漏放。
  • 锁的粒度尽量小。锁里别放慢操作，否则并发退化成串行。
  • 能不加共享状态就别加。传参、返回值、队列，都比共享变量安全。
G

进程：绕开 GIL 的过路费

要真并行算，就得多开解释器。ProcessPoolExecutor 干这事。

from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(4) as pool:
    results = list(pool.map(cpu_work, [n] * 4))

代价有三条，都不是小事。

代价 数字 说明
启动 约 0.07 秒 每次建池都要拉起子进程
传数据 看体积 参数和返回值都要序列化
传不了的东西 — lambda、闭包、连接对象、生成器

实测里 4 个计算任务从 0.46 秒降到 0.19 秒，没到 4 倍。启动和回传都在里面。

两条硬约束

第一，交给进程池的函数必须在模块级。不能在函数里定义，也不能在笔记本单元格里定义。

# 这样会炸，报 BrokenProcessPool
def work(n): ...
pool.map(work, [1, 2])

真实原因藏在子进程的 stderr 里：module '__main__' has no attribute 'work'。子进程是新的解释器，重新 import 你的模块，你内存里那份定义它看不到。

第二，脚本入口要写保护：

if __name__ == "__main__":
    main()

没有它，子进程 import 时又执行一遍建池，无限递归。

3.14 多了一个选择

InterpreterPoolExecutor：同一个进程里跑多个子解释器，各有各的 GIL。

实测 0.16 秒，比进程池的 0.19 秒还快。它比进程轻，但模块隔离和对象传递的限制更多。新东西，遇到再说。

H

asyncio：一个线程怎么同时等很多事

线程的极限在哪？每个线程要占内存，上下文切换也不免费。等一万个请求时，开一万个线程会先把自己压垮。

协程不靠操作系统。它在一个线程里，靠「主动让位」实现并发。

关键只有一句：await 是让位点。

  • 执行到 await，当前协程暂停，控制权交回循环。
  • 循环去找别的能干活的协程。
  • 等待的东西好了，循环把那个协程叫醒，从原地继续。

所以协程的并发是协作式的：你得主动让。不让，就没有并发。

一个阻塞调用毁掉全部

async def one():
    time.sleep(0.2)        # 错：整个线程卡住

async def one():
    await asyncio.sleep(0.2)   # 对：让位

5 个这样的协程，各「等」0.2 秒：

time.sleep      1.02s    ← 没有并发
asyncio.sleep   0.20s    ← 全并发

time.sleep 不会让位。它真的把线程按住 0.2 秒，循环里其他协程全在排队。

同一个坑，换成同步 requests.get、同步 open()、CPU 很重的解析，结果一样。这就是「全链路都得是异步」的意思。

非异步的库怎么办？丢进线程：

result = await asyncio.to_thread(blocking_func, arg)

四个常用组合

需求 写法
一起等，按输入顺序收 await asyncio.gather(*coros)
谁先回来先处理 async for f in asyncio.as_completed(coros)
单个超时 await asyncio.wait_for(coro, timeout=0.2)
整段超时 async with asyncio.timeout(0.2):

顺序差别不是细节。三个任务分别等 0.3、0.1、0.2 秒：

as_completed   ['b', 'c', 'a']
gather         ['a', 'b', 'c']

要边收边处理，比如往前端推流式输出，必须用 as_completed。gather 会等到最后一个。

I

生产三件套：限流、失败、超时

能跑通和能上线，中间隔着三件事。

第一件：限流

gather 会一次性把所有请求打出去。九个还好，九千个就是事故。

sem = asyncio.Semaphore(3)

async def one(i):
    async with sem:
        return await call(i)

await asyncio.gather(*[one(i) for i in range(9)])

9 个 0.2 秒的请求，上限 3 个，实测 0.60 秒，正好三批。峰值并发确实是 3。

第二件：失败

gather 默认遇到第一个异常就往外抛。此时其余任务还在后台跑，没人收结果。

results = await asyncio.gather(*coros, return_exceptions=True)

ok = [r for r in results if not isinstance(r, Exception)]
bad = [r for r in results if isinstance(r, Exception)]

这样一次请求炸了，其他结果还在。报告能写「9 个成功，1 个失败，失败的是第 3 个」。

第三件：超时

try:
    await asyncio.wait_for(coro, timeout=0.2)
except TimeoutError:
    ...

超时会取消那个协程。取消不是「不管了」，它会抛 CancelledError，让目标有机会清理。

三层都装齐，才算能上线。

J

选型：拿到活先问三句

别一上来就写代码，先问三句。

三句对应的就是前面三节：

  1. 只有一个？串行。并发是放大吞吐，不加速单次调用。
  2. 在算？进程。线程白搭。
  3. 在等，而且路数很多？协程加限流。几十路以内，线程池更省心。

还有一条反直觉的建议：先串行跑通，再改并发。并发引入的 bug 会掩盖真正的逻辑错误。你分不清是逻辑错了还是调度错了。

最后一句话

并发不提升单次速度，只提升吞吐。你每加一层并发，就多一份调度、竞态、超时的复杂度。

只有当「等」明显拖慢了整体，才值得付出这笔复杂度。否则串行就是最好的并发。
