A

速览

并发不是「多加线程」。先看瓶颈在烧 CPU 还是在等 I/O，再决定用哪个工具。

三种写法都能跑通「任务并行」，但只有一种能真正加速当前瓶颈。选错的代价是多写代码、多踩坑，速度一点没变。

练习见 codes/concurrency/qa.ipynb，负载在 codes/concurrency/bench.py。

B

四个候选

写法 并发单元 能加速什么 代价
串行 无 什么都不加速 慢，但最好调
ThreadPoolExecutor 线程 I/O 密集 受 GIL 限制，CPU 活不加速
ProcessPoolExecutor 进程 CPU 密集 启动贵，数据要能 pickle
asyncio 协程 海量 I/O 全链路得是异步的
InterpreterPoolExecutor 子解释器 CPU 密集 3.14 新增，生态还在跟进

InterpreterPoolExecutor 和进程池解决同一个问题：绕开 GIL。它比进程轻，但模块导入和对象传递的约束更多。

C

实测：两种瓶颈，两种结论

同一台机器（10 核），bench.cpu_work 每次约 0.12 秒。

场景 串行 线程 进程 子解释器
4 次 CPU 计算 0.46s 0.46s 0.19s 0.15s
8 次 0.2s 网络等待 1.63s 0.21s — —
  • CPU 密集：加线程耗时不变。线程之间在抢同一把 GIL。
  • I/O 密集：8 个线程把 1.63 秒压到 0.21 秒。等待时 GIL 是放开的。
  • CPU 密集换成进程，4 个任务从 0.46 秒到 0.19 秒。没有到 4 倍，因为进程启动和结果回传都要时间。
D

GIL 限制的是什么

GIL 是解释器级别的锁。同一时刻只有一个线程在跑 Python 字节码。

  • 纯 Python 运算全程拿着 GIL，多线程只能轮流跑。
  • 阻塞的 I/O 会主动放开 GIL，这时别的线程可以进来。
  • numpy、hashlib、zlib 这类 C 扩展在重活里也会放开 GIL。

推论：如果你的 CPU 活已经被 numpy 向量化，线程也可能有效，先量再说。

E

asyncio 骨架

async def call(i): ...

async def main():
    results = await asyncio.gather(*[call(i) for i in range(9)])
    return results
需求 写法
一起等，按输入顺序收 await asyncio.gather(*coros)
谁先回来先处理 async for f in asyncio.as_completed(coros)
单个超时 await asyncio.wait_for(coro, timeout=0.2)
整段超时 async with asyncio.timeout(0.2):
一个失败不影响别人 gather(..., return_exceptions=True)
失败就取消整组 async with asyncio.TaskGroup() as tg:

gather 默认遇到第一个异常就往外抛。此时其余任务还在后台跑，没人收结果。要一条条report，就加 return_exceptions=True。

F

限流：一次只放 N 个

sem = asyncio.Semaphore(3)

async def one(i):
    async with sem:
        return await call(i)

await asyncio.gather(*[one(i) for i in range(9)])

9 个 0.2 秒的请求，上限 3 个，实测 0.60 秒。正好是三批。

调模型接口必须有这一层。没有它，gather 会一次性打满服务端。

G

进程池的硬约束

子进程是新解释器，它重新 import 你的模块，拿不到父进程的内存。

  • 传给进程池的函数必须定义在模块级，不能是闭包，也不能在笔记本单元格里定义。
  • 参数和返回值必须能 pickle。连接对象、生成器、lambda 都传不过去。
  • 脚本入口要写 if __name__ == "__main__":，不然 spawn 会无限递归。
  • macOS 和 Windows 默认用 spawn，Linux 默认 fork。spawn 更严格，按它写才跨平台。

笔记本里报的是 BrokenProcessPool。真正的原因（AttributeError）在子进程的 stderr 里，往上翻第一条 Traceback。

H

笔记本两个坑

asyncio.run(main())
# RuntimeError: asyncio.run() cannot be called from a running event loop

Jupyter 的内核已经有一个在跑的事件循环。单元格里直接用顶层 await，不要再包一层 asyncio.run。

第二个坑是进程池：

def work(n): ...          # 定义在单元格里
ex.map(work, [1, 2])      # BrokenProcessPool

把它挪进 bench.py 这种可导入的模块，问题就没了。

I

常见坑

  • 协程里调 time.sleep 或同步 requests。整个事件循环停住，5 个 0.2 秒的任务要 1.02 秒。
  • 用线程池算 CPU 活。耗时和串行一模一样，还多了一层调度开销。
  • gather 不用 return_exceptions，一个失败就丢掉全部结果。
  • create_task 的返回值不保存。任务可能被垃圾回收，提前取消。
  • 进程池里传 lambda 或闭包。序列化阶段就失败。
  • 给 I/O 任务开几百个线程。内存和上下文切换都扛不住，换 asyncio 或加信号量。
  • 用 asyncio.run 嵌在已有循环里。笔记本、FastAPI、Jupyter 都会踩到。
J

什么时候别并发

  • 只有一个请求。并发没有收益，只多一层代码。
  • 任务之间有严格顺序。并发要靠信号量或队列把顺序再加回来，不如写清楚。
  • 数量很少、每次很快。线程池的启动开销可能比省下的时间还多。

并发是放大吞吐的工具，不是提速单次调用的工具。
