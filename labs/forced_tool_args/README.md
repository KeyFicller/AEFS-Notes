# 强制工具调用 × 参数抽不出来

问题：`tool_choice="any"` 让模型必须调用工具，但输入里根本没有参数。它会怎么填，填错了会怎样？

复现：`.venv/bin/python labs/forced_tool_args/run.py`（真实 API，`deepseek:deepseek-chat`，约 15 秒）。
输入固定在 `帮我订张去上海的票，越快越好。`——出发城市、日期、乘机人编号全缺。

| 场景 | 强制 | 参数校验 | 结果 |
| --- | --- | --- | --- |
| S0 | 不强制 | 宽松 | 直接问用户，不填（换一次采样也可能直接文字回答） |
| S1 | 每轮 | 宽松 | 编造 `北京 / 2025-01-01 / P000000`，**同一张票反复下单**，撞 `recursion_limit` |
| S2 | 仅首轮 | 宽松 | 编造并**真的出票**（有时连 `P482913` 这种合法编号都猜中），事后才说「有几个信息我是靠猜的」 |
| S3 | 仅首轮 | 严格 | 校验报错，模型改口问用户，一轮收敛 |
| S3b | 每轮 | 严格 | 换说法继续撞，全失败，撞 `recursion_limit` |
| S4 | 仅首轮 | 严格 + 澄清工具 | 直接调 `ask_clarification`，一次都没编 |
| S5 | 不强制（prompt 硬逼） | 严格 + 澄清工具 | 同上，挑澄清工具 |
| S6 | — | — | `deepseek-v4-flash` 思考模式 400：`Thinking mode does not support this tool_choice` |

采样有随机性：具体填什么值、有没有主动提问，每次跑都不一样；上表是行为类别，不是固定字面量。

## 加一条提示词：自主完成、不问用户

要测的就是那个问题——「说了自主完成，模型是会自己编参数，还是照样问？」直接测了两档提示，各场景跑 3 次：

- **弱**：`你能自主完成的就自主完成，不要向用户提问，也不要让用户补充信息。`（S7–S10）
- **强**：`你是一个全自动订票系统。禁止向用户提问，禁止要求用户补充信息，禁止说「需要确认」「请提供」。缺的参数自己按最合理的方式决定并立即下单。`（S11–S13）

| 场景 | 提示 | 校验 / 出口 | 3 次里的表现 |
| --- | --- | --- | --- |
| S7 | 弱 | 严格 + 澄清工具 | 3/3 在**文字里**问用户，没调澄清工具 |
| S8 | 弱 | 严格 | 3/3 文字里问，1 次还替用户把日期假定成今天 |
| S9 | 弱 | 宽松 | 3/3 文字里问 |
| S10 | 弱 | 严格 + 澄清工具 + 首轮强制 | 3/3 调 `ask_clarification` |
| S11 | 强 | 宽松 | **3/3 编造并真的出票**，事后补一句「我采用了默认值」 |
| S12 | 强 | 严格 | 1/3 猜中 `P482913` 过了校验、真出了错票；2/3 不调工具，文字里说缺什么 |
| S13 | 强 | 严格 + 澄清工具 | 2/3 调 `ask_clarification`，1/3 文字里问 |

结论：

**1. 弱提示基本无效。** 「能自主就自主」被当成软建议，模型照样问，只是把问题写在文字里而不是调工具。行为没变，形式变了。

**2. 强提示能把「问」压下去，但压出来的不是能力，是编造。** S11 三次全部编造 `北京 / 若干日期 / P482913` 并真的出票——注意它编的是「看起来合理」的值，不是空字符串，所以下游毫无察觉。

**3. 提示词不是决定性的那一层，schema 和出口才是。** 同一个强提示，宽松 schema 下 3/3 编，严格校验下只有 1/3 编、其余转向说明。可见真正决定「编不编」的是校验能不能拦住、以及有没有合法出口可走。

**4. 最危险的是「校验形式上存在、但能靠猜命中」。** S12 那次 `passenger_id` 猜对了唯一注册的 `P482913`，`origin` 和 `depart_date` 明明是编的却一起过了校验，工具返回「已出票」。校验器只保护了它检查的那几个字段，其余字段照样被静默填满。

## 观察

**1. 强制拿掉的只是「不打工具」这个选项，不是「不知道就编」。**
模型只剩两条路：编一个值，或者调用另一个工具。没有第三条。所以强制和「参数可抽取」是两件独立的事，前者对后者零帮助。

**2. 编出来的值会真的执行。**
S2 的 `book_flight` 参数是编的，工具却返回 `已出票 ...`，没有任何报错。更阴的是它偶尔会猜中合法的乘机人编号——于是校验也过了，只有日期是虚构的，下游看起来就是「下单成功」。模型事后承认是猜的，但副作用已经发生——这正是 prompt 层面拦不住的地方。

**3. 每轮强制 = 图无法自然终止。**
`tool_choice="any"` 把最终文字回答也堵死了，S1 里模型想收尾却没有出口，只能反复调工具。所以真实系统要么只在第一轮强制，要么在工具结果后放开 `tool_choice`（本实验的 `force="first"`）。

**4. 业务校验把「静默编造」变成「可恢复错误」。**
S3 加了格式 + 注册表校验，`ToolNode` 把异常包成 `status="error"` 的 `ToolMessage`，模型下一轮就改口问用户。校验器不负责拦住幻觉，它负责把幻觉变成模型看得见的事实。

**5. 最坏组合是「每轮强制 + 校验必失败」（S3b）。**
错误信息不给出路，模型只是把 `北京` 换成 `待确认` 继续撞，直到 `recursion_limit`。生产里这就是一次重试风暴，白烧 token 还占着 worker。

**6. 最省事的解法是给一条合法出口（S4）。**
`ask_clarification` 让强制照样生效，但模型有地方可去，一次都没编。这条出口的成本只是一个空工具 + 一句 description。

**7. 思考模型根本不吃 `tool_choice`。**
`deepseek-v4-flash` 返回 400。要用这个机制得换非思考模型（`deepseek-chat`）。拿 prompt 当替代品（S5、S11–S13）时结果完全由校验和出口决定：有澄清工具就走向提问，schema 宽松就走向编造，跟 prompt 写得多强硬关系不大。

## 落地清单

- 只在必须动手的第一轮强制；拿到工具结果后释放 `tool_choice`。
- 一定给 `ask_clarification` 这类出口，并且写在 tool description 里。
- **别指望「自主完成、不问用户」这类提示词能让模型自己搞定**：它要么把问题换成文字说辞，要么开始编。要它必须动手，用 `tool_choice`；要它别乱编，用校验。
- 工具参数上加业务校验（格式、枚举、注册表），不信任模型填的值；每个必填参数都要有校验，只校验一两个字段等于给编造留后门。
- 永远设 `recursion_limit`，它同时是「强制档」的熔断器。
- 需要指定某个工具而不是「任意工具」时，用 `tool_choice={"type": "function", "function": {"name": ...}}`。
